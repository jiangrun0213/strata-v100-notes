# Strata 双 V100 深度速度基准

日期：2026-10-03 ｜ 引擎：Strata v0.17.0 @ 127.0.0.1:18200 ｜ 硬件：2×V100-SXM2-16GB（NVLink NV6, peer-tier）
模型：Qwen3.8-Flash-Next-125B IQ3_S ｜ 口径：客户端 OpenAI API 实测 + 服务端日志双口径交叉验证

## 一、结论速览

| 指标 | 结果 | 说明 |
|---|---|---|
| **解码（≥512 tok 输出）** | **59~63 tok/s 稳定** | 三档梯度三连测，波动 <5% |
| 解码（短输出 128 tok 热身后） | 68~82 tok/s | 短输出时 MTP 命中率高 |
| **Prefill（14.5K tokens）** | **765 tok/s** | 长输入吞吐，随长度递增 |
| Prefill（3.7K tokens） | 459 tok/s | |
| **TTFT（133 tok prompt）** | ~3.4 s 冷 / 首批后流式 | 含检查点+首批生成 |
| KV 复用（同 prompt 第二次） | **8017 ms → 58 ms（138×）** | 3679/3684 tokens 命中 |
| MTP 草稿接受率 | 70.5%（基准期间）/ 71.5%（日常） | 与日常使用一致 |
| 流式 chunk 间隔 | p50 ≈ 0 ms / p95 = 65 ms | 服务端批量推 token，无卡顿 |

## 二、测试方法

1. **Prefill 梯度**：构造 4 档长度 prompt（~128/1K/4K/16K tokens），max_tokens=8 非流式，
   用服务端 usage.prompt_tokens 与耗时计算 prefill 吞吐
2. **解码梯度**：max_tokens = 128/512/2048 × 3 次，短 prompt（133 tok），
   服务端 completion_tokens / 生成毫秒
3. **KV 复用**：同一 3.7K prompt 连发两次对比
4. **流式分布**：2048 tok 输出流式请求，统计 chunk 间隔分位数
5. 双口径：客户端计时（含 HTTP 开销）与 `strata serve:` 日志（纯引擎计时）交叉

## 三、详细数据

### Prefill 梯度（冷缓存）

| 目标长度 | 实际 prompt | 服务端耗时 | **吞吐** |
|---|---|---|---|
| ~128 | 186 tok | 4060 ms | 45.8 tok/s * |
| ~1K | 981 tok | 6342 ms | 154.7 tok/s |
| ~4K | 3684 tok | 8009 ms | **460 tok/s** |
| ~16K | 14549 tok | 19025 ms | **765 tok/s** |

\* 超短 prompt 的固定开销（KV 初始化/检查点）占主导，速度数字失真；真实含义是"小输入也要 ~3.5s 出首 token"。

**梯度规律**：吞吐随 prompt 长度显著上升（固定开销摊薄 + CUDA Graph 批处理效率），长文档场景收益最大。

### 解码梯度（服务端口径，短 prompt=133 tok）

| max_tokens | 三次实测 (tok/s) | 均值 |
|---|---|---|
| 128 | 63.2 / 68.4 / **81.6** | 71.1（热身后走高） |
| 512 | 58.2 / 59.1 / 59.9 | 59.1 |
| 2048 | 62.6 / 62.1 / 60.5 | 61.7 |

- 128 tok 三连测递增（63→82）：引擎热身（专家缓存预热、检查点建立）
- **512 与 2048 档几乎一致（59~62）→ 解码速度与输出长度无关，稳定平台期**

### KV 缓存复用

| 请求 | 服务端 prefill 耗时 | 复用 |
|---|---|---|
| 同一 3684 tok prompt 第 1 次 | 8017 ms（全新读取） | 0/3684 |
| 第 2 次 | **58 ms** | **3679/3684 (99.9%)** |

多轮对话（dsh-harness 长会话实测）中历史 KV 复用率 97.6%——append-only 会话几乎零 prefill 成本。

### 流式体验（2048 tok 输出）

```
TTFT:            11.7 s（含 3.4s prefill + 首个大 batch）
chunk 间隔 p50:  0 ms（服务端每批推多个 token）
chunk 间隔 p95:  65 ms
整体:            1460 chunks / 32.5s ≈ 63 tok/s
```

### MTP 推测解码

- 基准期间接受率 70.5%（28,771/40,798）
- 日常会话全局 71.5%（24,317/34,031）
- 2048 tok 长输出时 ~65%（1,050/1,593）；短输出时更高（128 tok 档 ~78%）

## 四、与部署基线及日常使用的对照

| 口径 | 速度 |
|---|---|
| 部署时固定 700 tok 基线 | 44.8 tok/s |
| **本基准平台期（512/2048）** | **59~62 tok/s** |
| dsh-harness 日常使用加权（100 请求） | 59.2 tok/s |
| 短输出热身峰值 | 82 tok/s |

三者互相印证：**59~63 tok/s 是这台双 V100 跑 125B MoE 的真实平台**。部署时 44.8 偏低是
因为单次冷启动测试含热身损失；QSA scorer 的 sm_80+ tf32-mma 依赖使 sm_70 停留在
fp32-FMA 回退路径 —— 这是结构性天花板，软件调优已到头（hugepages/CPU 调频/校准参数均验证无效）。
